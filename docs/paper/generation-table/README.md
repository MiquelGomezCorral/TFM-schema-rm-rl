# Generation table: ARM-FM against FARM, per suite

Date: 2026-11-14, from the bundles of the main checkout at `b332ecf` (box-carry and forced-start
included). Every bundle was generated by the same model pair: writer `deepseek-v4.1-flash`, critic
`glm-5.3-flash`, reasoning `none`, 10 attempts. A count of how often each generation step was accepted
and what it cost, not a measure of machine quality.

## What it shows

accepted, how many tries and model calls a bundle took, and how many labelings were accepted at
generation and passed the check after repair.

Reading, on these cards and this model pair: the compiler arm (FARM) got its machine accepted on all
124 main-suite bundles, in 1.23 tries on average; ARM-FM, which writes the whole machine, needed 2.42
and failed on 3 (`tpl-not-co-existence-1-goal~p1`, `tpl-not-co-existence-1-nogoal`,
`tpl-not-co-existence-1-nogoal~p3`: no accepted machine). After the repair loop both arms end with
almost every labeling passing (124/124 and 123/124). One model pair, one run per bundle: a data point,
not a rate.

## Caveats the table needs

- **Retries.** The table counts a bundle by its last run. A bundle retried after a failed first run
  shows the retry's tries (the 3 failed forced-start bundles needed 2 RM tries the first time and 1
  after). The only retry loop the table counts apart is FARM's labeling regeneration (column "FARM
  labeling regenerated"); ARM-FM labelings were not regenerated.
- **Three FARM bundles keep an older labeling.** The FARM labelings of all 124 main-suite bundles were
  regenerated with the RM-only vocabulary rule (118 accepted). For `cx-goal-many-rules~p2`,
  `tpl-not-co-existence-1-nogoal` and `tpl-responded-existence-2-goal` the regeneration failed twice and
  a failed loop leaves a complete bundle as it was, so each keeps the labeling written before the rule
  (full vocabulary). All three pass the check. All three are BlockedUnlockPickup cards, and each failed
  3 tries twice, always on `blocker_moved` (the cell in front of the door holds no ball): the writer
  sent code the sandbox refuses (syntax error, unknown name, private attributes), logic the critic
  rejects (any ball on the grid instead of the one cell), or left a proposition out. The old labeling
  passed review and the check, so it stays. The narrower prompt made the same model behave
  differently, so labeling-function generation is not robust either and needs attention, but the paper
  does not test it. Two more (`tpl-precedence-1-goal~p1`,
  `tpl-not-co-existence-1-nogoal~p3`) hold a labeling the repair loop wrote after the regeneration
  failed. The old attempts stay in each `<name>.labeling_regen.json` beside the bundle.
- **One FARM bundle has no labeling: `tpl-existence-2-nogoal`.** Its machine was accepted, the labeling
  failed (repair loop `unfixed` after 10 rounds), so it is "RM accepted, labeling failed", not trainable.
  This is the 1 missing of 124 in "ok after repair" for FARM (95/96 in templates).
- **27 FARM bundles were restored from logs** (1 base, 5 complex, 21 templates; the column "restored
  from log"). Their machine was accepted but the run failed at labeling before the bundle was saved, so
  the machine was rebuilt from the log's serialized machine and flagged `restored_from_log`. Their
  labeling tries are unknown, so the "labeling tries" column leaves them out; the calls are from the
  original run's status file.
- **Ablation bundles are derived, not generated.** `ablate-rm` copies a FARM bundle and turns one
  reward part off, so each of the 3 cards (`cx-goal-many-rules`, `cx-goal-one-rule`, `cx-rules-only`)
  gives 6 bundles that repeat the source's stamp. The table prints them as an "ablation" row (18 FARM
  bundles, 12 restored because 2 of the 3 sources were restored); they are not in the main-suite total
  and their counts say nothing about generation. The 18 are not in the table above.
- **The calls column** is the call count of the bundle's last generation run, from its status file. It
  leaves out the regeneration and repair calls, so it is below the true spend on FARM main-suite
  bundles. The pilot status files have no count.
- **One model pair, one run per bundle.** ARM-FM prompts are untouched. Do not read a gap between the
  arms as a rate.

## Per card

[`cards.md`](cards.md) lists the 150 bundle names the table counts (4 base, 24 complex, 96 templates,
16 box-carry, 8 forced-start, 2 pilot), each with its natural-language task (the paraphrase text for a
`~p<k>` name) and the card's expected LTLf, and under each suite heading the path of the two machines:
`experiments/benchmark/<suite>/bundles/{arm-fm,farm}/<bundle>/reward_machine.txt`. ARM-FM writes the
machine directly and has no LTL of its own; the LTLf shown is the benchmark's reference clause list, not
what a model compiled. The machine files are git-ignored outputs, so they are in the main checkout, not
in this repository.

## Evidence

- `generation-table.json` and `generation-table.md`: the output of the repo command over every suite
  under `experiments/benchmark`.
- `calls-table.md`: calls per bundle from the status files. box-carry matches the generation run's own
  total (ARM-FM 158, FARM 91 calls).
- `cards.md`: the 150 cards behind it. Its counts match the bundle folders on disk (every suite and arm).

## Rerun

From the main checkout (the bundles are not in git), inside `RM_RL_env`; no model call:

```bash
PYTHONPATH=app python app/main.py generation-table --root experiments/benchmark \
    --output <dir>/generation-table.json > <dir>/generation-table.md
python -I docs/paper/generation-table/check/calls_table.py experiments/benchmark > <dir>/calls-table.md
PYTHONPATH=app python -W ignore docs/paper/generation-table/check/cards_list.py <dir>/cards.md
```

The first command prints a last line `wrote <dir>/generation-table.json`; the copy in this entry has it
removed. `cards_list.py` ends with `wrote <dir>/cards.md: 150 bundle names`.
