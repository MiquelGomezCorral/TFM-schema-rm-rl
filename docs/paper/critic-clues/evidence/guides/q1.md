## Compiler clues

The user prompt may carry a `Compiler clues` section. The compiler computes it exactly from the
candidate clauses and the machine, so it is never wrong about what the clauses demand. It knows
only the clauses, not the level: a sequence it shows may be impossible in practice. Read each clue
against the task sentence:

- `Rules in plain words`: what each clause demands, when it becomes owed or is broken for
  good, and what failing it costs. A line that says something the task does not say is a wrong
  template, order, event or priority. Example: task "pick it up on your very next move", line
  "every box_fell is followed by holding_box, on that step or later": the task needs
  `ChainResponse`.
- `Every way to finish includes`: the events no finishing run avoids, whatever their order.
  An event the task commands that is missing here has no goal clause; an event here that no
  sentence asks for comes from an added clause. Example: task "carry the box to the exit", clue
  "includes: at_exit": nothing makes the agent hold the box.
- `Doing nothing`: what an agent that never acts gets. When the task commands an action
  unconditionally and as a hard requirement (checklist 2) and doing nothing still keeps every
  hard rule, a goal is missing. Example: task "Flip the switch", clue "Doing nothing: keeps every
  hard rule". A task made only of rules, conditionals or preferences keeps every hard rule when
  idle, and that is right.
- `Redundant`: a hard clause the other hard clauses already imply, so the machine is the
  same without it. Ask to drop it, usually the `Existence` of an earlier step of a `Precedence`
  chain, and keep the chain and the `Existence` of the last step.
- `Rule status per state`: which clauses each machine state still owes, has kept so far, or
  has broken. Use it to read the machine instead of tracing guards.

The clues never replace the task: a clause no sentence states is still an added requirement, and
a clue that matches the task is no reason to reject.
