# Correction to Algorithm 1

The PDF extraction flattened the piecewise definition of the DQN target in line 20
of Algorithm 1.

The intended expression is:

\[
y_j =
\begin{cases}
R_j^{\mathrm{total}},
& \text{if the episode terminates at step } j+1, \\[4pt]
R_j^{\mathrm{total}}
+ \gamma \max_{a'}
\hat{Q}\left(s_{j+1}, \phi(u_{j+1}), a'; \theta^{-}\right),
& \text{otherwise.}
\end{cases}
\]

Thus the complete semantic meaning of lines 19--21 is:

1. Sample a random minibatch of transitions

   \[
   (s_j,u_j,a_j,R_j^{\mathrm{total}},s_{j+1},u_{j+1})
   \]

   from replay memory \(D\).

2. Construct the target

   \[
   y_j =
   \begin{cases}
   R_j^{\mathrm{total}},
   & \text{terminal transition},\\
   R_j^{\mathrm{total}} +
   \gamma \max_{a'}
   \hat Q(s_{j+1},\phi(u_{j+1}),a';\theta^-),
   & \text{otherwise}.
   \end{cases}
   \]

3. Perform a gradient-descent step on

   \[
   \left(
   y_j-Q(s_j,\phi(u_j),a_j;\theta)
   \right)^2.
   \]

No substantive algorithmic step was missing from the extracted Markdown; the issue
was the loss of the visual structure of the piecewise equation.

## MiniGrid

Figures 6 and 7 report learning curves for DoorKey and more difficult long-horizon
MiniGrid tasks.

The text states that ARM-FM:

- consistently performs better than the evaluated baselines on DoorKey;
- works on both fixed and procedurally generated layouts;
- solves UnlockToUnlock, BlockedUnlockPickup, and KeyCorridor;
- reaches near-perfect reward on these harder tasks while the reported baselines

The experiments are averaged over **3 independent random seeds**, with shaded

## Craftium

The Craftium task requires gathering resources in sequence before mining a diamond:

1. wood;
2. stone;
3. iron;
4. diamond.

The underlying environment only gives its sparse task reward when the final diamond
is collected.

The paper reports that PPO with the generated LARM learns the complete task sequence,
whereas baseline PPO makes minimal progress.

The paper compares SAC trained from sparse rewards with SAC receiving the

The authors report higher success rates for the RM-guided agent on most evaluated
manipulation tasks.

Additional appendix experiments report that:

- better hyperparameter tuning can yield high success rates with the RM-guided agent;
- RM rewards can be combined with intrinsic exploration such as RND;
- the combination generally improves performance in the reported experiments.

# Clarification of Zero-Shot Generalization

The paper uses **zero-shot generalization** in a specific sense.

It refers to:

> zero-shot generalization across novel task compositions within the same domain

and **not** to cross-domain transfer.

The policy is trained on tasks \(T_A\) and \(T_B\), whose LARMs expose a collection
of sub-goal embeddings. At evaluation time it receives a newly generated LARM for
an unseen task \(T_C\).

Zero-shot success is possible when the subtasks represented in \(T_C\) are
semantically related to skills/subgoals encountered during training.

Thus, the zero-shot claim should not be interpreted as the agent acquiring entirely
new low-level capabilities without training. Rather, the experiment demonstrates
recomposition and reuse of semantically familiar skills in a previously unseen task
composition.

# Clarification of the Optimality-Preservation Guarantee

The statement in the main text that LARMs provide theoretical guarantees should not
be interpreted as applying to arbitrary FM-generated reward functions without
conditions.

Appendix A.5 gives the following condition.

Let the original sparse task be an MDP \(\mathcal{M}\), and let the LARM induce the
cross-product MDP \(\mathcal{M}_{\mathrm{LARM}}\).

The generated LARM must satisfy:

1. **No positive reward cycles.**

   For every cycle returning to an RM state \(u_i\),

   \[
   u_i \rightarrow \cdots \rightarrow u_i,
   \]

   the cumulative LARM reward around that cycle must be less than or equal to zero.

2. **Dominant terminal reward.**

   The final reward \(R_{\mathrm{goal}}\), obtained when transitioning to an accepting
   state, must be strictly greater than the cumulative reward obtainable from any
   non-terminal trajectory.

Under these conditions, a policy that is optimal for
\(\mathcal{M}_{\mathrm{LARM}}\) is also optimal for the original sparse-reward MDP.

The purpose of the first condition is to prevent an agent from exploiting an
intermediate-reward loop instead of completing the task.

For example, in the UnlockPickup LARM:

- acquiring the key gives \(+0.1\);
- subsequently losing the key and transitioning back gives \(-0.1\).

The resulting cycle has zero cumulative reward rather than positive cumulative
reward.

The DoorKey LARM similarly contains a zero-sum cycle.

The Craftium LARM is a directed acyclic graph, so it contains no reward cycles.

The paper states that the remaining experimental LARMs also satisfy this property.

# Human Verification Is Optional but Was Used in Some Experiments

ARM-FM contains a generator/critic FM self-improvement loop. A human operator can
optionally replace the critic during a refinement step.

Human intervention was **not uniformly required across all experiments**.

The paper reports:

| Environment | Human intervention | Description |
| :--- | :---: | :--- |
| MiniGrid-DoorKey (all sizes) | No | FM self-improvement was sufficient; a human check confirmed correctness after 3 iterations. |
| MiniGrid-UnlockPickup | Yes | The initial LARM missed the case where the agent drops a key after pickup. Human feedback requested a transition representing the resulting loss of progress. |
| MiniGrid-BlockedUnlockPickup | No | FM self-improvement was sufficient. |
| MiniGrid-KeyCorridorS3R3 | Yes | The original LARM was too sparse. Human feedback suggested intermediate progress rewards such as crossing doors or entering rooms. |
| Craftium | No | The FM generated an effective task decomposition without human guidance. |
| XLand-MiniGrid | No | No human intervention was used for the 1,000 generated LARMs; correctness was evaluated automatically using the LLM-as-judge procedure. |
| Meta-World (all tasks) | Yes | The initial reward values produced local minima. A human rescaled rewards for particular events without changing the event definitions. |

Therefore, the framework permits fully automated LARM generation, but some reported
experiments benefited from human refinement.

# LLM-as-Judge Evaluation Clarification

For the analysis of FM generation quality, the authors sample **1,000 XLand-MiniGrid
tasks** and ask models from several families to generate:

1. the Reward Machine structure;
2. Python labeling functions;
3. natural-language state instructions.

The generated artifacts are evaluated using an LLM-as-judge protocol.

The judge is:

**Qwen3-30B-A3B-Instruct-2507**

and is stated not to be one of the models that generated the evaluated LARMs.

The paper reports a model-scale trend in which larger foundation models generate
fully correct task specifications more reliably.

It also observes model-specific differences: for example, Mistral-Small performs
better at producing valid Reward Machine structure than at producing correct
labeling code, emphasizing that these two outputs require somewhat different
capabilities.

# State-Embedding Analysis Clarification

The semantic embedding analysis uses the state instructions generated for the
1,000 XLand-MiniGrid LARMs.

The embeddings are obtained using:

**Qwen3-30B-A3B-Instruct-2507**

and visualized using PCA.

The paper reports that:

- start-state instructions,
- intermediate-state instructions, and
- end-state instructions

occupy distinguishable regions of the embedding space.

Semantically similar state instructions from different tasks also cluster together.

The authors interpret this as evidence that the state-description embeddings provide
a shared semantic skill space that allows one policy to reuse behavior across
different Reward Machines.
